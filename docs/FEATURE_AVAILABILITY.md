# Offline research feature-availability check — issue #77

`alphora.research.feature_availability` is a bounded **synthetic-only, read-only** preflight for one research decision's price/news input-version chronology. It checks that the reported feature measurement window finishes before reported first receipt, the exact version is available after first receipt, and **all precede the decision time strictly**. It requires an independently supplied SHA-256 pin for every input artifact and emits a deterministic local SHA-256 receipt. Caller-supplied order and timezone representation do not change the receipt; input-version changes do.

**Asset-binding limitation and schema 2:** Every `FeatureEvidence` now requires a caller-declared `asset_id` equal to the `ResearchFeatureDecision.asset_id` for both PRICE and NEWS inputs. The guard rejects reuse of an **unmodified** SPY-tagged input in a QQQ decision and includes the per-input asset association in a version-2 fingerprint. A shared market/news article may be represented by separately declared *derived* per-asset inputs, but copying an artifact hash and changing every claimed asset ID can still pass with a **different** receipt: the guard cannot authenticate asset relevance, vendor identity, timestamp history or cross-asset exposure. Independently pinned, externally validated asset-to-source mapping is required before treating this as trusted point-in-time evidence. Old version-1 receipt pins intentionally do not match version 2.

It is **not** a model, data ingestion pipeline, price oracle, source authentication, backtest, LEAN run, trading eligibility engine, or proof of point-in-time truth. The local receipt cannot prove that a vendor sent the data at the claimed time. The caller must obtain first-seen/available timestamps and artifact digests from a trusted, independently reviewed off-repository source. Publication time alone does not prove earliest availability, especially for news. The decision records source IDs and timestamps but **not underlying feature values**; models must separately validate window construction, training-only fitting, corporate actions and data leakage.

For model evaluation, continue to reuse merged `walk_forward.py` (purge, embargo, untouched holdout), existing `catalysts.py` (news trust), and `market_manifest.py` (candidate calendar/universe claims). Future integration must audit every actual example, not only a sample, validate article syndication/deduplication, label maturity and cross-asset exposure, and independently pin complete vendor receipts under #20. A positive feature receipt must **never** authorize execution or support a real-market performance claim.

Run `python -m unittest tests/test_feature_availability.py -v` in a full checkout. No broker credentials, Alpaca integration, external datasets, model dependencies, HTTP requests or orders. Existing $100,000 simulated initial equity, 0.5% per-trade planned risk, 10% allocation cap, 2% daily halt and daily rebalancing are unchanged and **not enforced by this research helper**.
